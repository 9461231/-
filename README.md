# 中小型超市运营管理系统设计与实现 —— 毕业设计分阶段开发路线

> 项目定位：本科软件工程专业毕业设计  
> 题目：**中小型超市运营管理系统设计与实现**  
> 开发原则：**一个模块一个模块实现；当前模块完整跑通后，再进入下一模块。**  
> 系统目标：完成一个具有完整零售业务闭环的中小型超市运营管理系统，并在业务系统之上加入可落地的 **AI Agent + MCP** 智能运营能力。

---

## 一、项目总体定位

本项目不是单纯的“增删改查管理系统”，而是一个围绕中小型超市实际运营流程设计的业务系统。

核心业务链条：

```text
商品
  ↓
供应商
  ↓
采购
  ↓
库存
  ↓
销售
  ↓
会员 / 促销
  ↓
盘点与损耗
  ↓
经营分析
  ↓
AI 智能运营 Agent
```

项目主体仍然是传统的软件系统，Agent 作为智能增强层接入真实业务数据和业务操作能力。

# 四、核心业务模块规划

为了满足导师提出的“**七个以上核心业务模块，不含登录、系统管理等公共模块**”，规划为 9 个核心业务模块：

| 阶段 | 模块 | 核心程度 |
|---|---|---|
| Step 01 | 商品信息管理 | 核心 |
| Step 02 | 供应商管理 | 核心 |
| Step 03 | 采购管理 | 核心 |
| Step 04 | 库存管理 | 核心 |
| Step 05 | 销售管理 | 核心 |
| Step 06 | 会员管理 | 核心 |
| Step 07 | 促销管理 | 核心 |
| Step 08 | 盘点与损耗管理 | 核心 |
| Step 09 | 经营分析 | 核心 / 业务扩展 |
| Step 10 | AI 智能运营 Agent | 智能增强层，不用于凑核心模块 |

即使导师不将“经营分析”计算为核心模块，前 8 个模块仍然能够满足“7 个以上”的要求。

# 五、严格的开发原则

## 原则 1：一次只实现一个模块

每个阶段必须形成：

```text
数据库
  ↓
Entity
  ↓
Repository
  ↓
Service
  ↓
Controller
  ↓
API
  ↓
前端页面
  ↓
真实数据库联调
```

当前模块没有完整跑通之前，不开始下一个模块。

---

## 原则 2：不为了凑模块拆分

模块必须对应真实业务边界。

例如：

- 商品
- 采购
- 库存
- 销售

是不同业务域，不是把一个 CRUD 页面硬拆成四个模块。

---

## 原则 3：传统业务逻辑优先保证确定性

涉及：

- 金额计算
- 库存扣减
- 库存增加
- 订单状态
- 积分计算
- 促销规则

等关键业务逻辑，使用传统程序代码完成。

LLM 负责：

- 理解自然语言
- 任务规划
- 工具选择
- 数据解释
- 生成建议

而不是直接决定数据库底层逻辑。

---

## 原则 4：Agent 最后接入

不在前期为了“有 AI”而加入聊天框。

Agent 必须建立在真实业务数据和成熟业务 API 之上。

# 八、第一版 Agent 不做“万能助手”

建议先聚焦三个业务方向：

## 1. 智能补货 Agent

用户：

```text
“最近有哪些商品需要补货？”
```

Agent 调用：

```text
get_inventory_alerts()
get_sales_history()
get_product_info()
get_supplier_info()
```

然后分析：

```text
预计销量
+
安全库存
-
现有库存
=
建议采购数量
```

进一步支持：

```text
“按照最近7天销量，帮我制定一份5000元以内的补货方案。”
```

Agent 最终生成：

```text
商品 A × 100
商品 B × 60
商品 C × 80

预计金额：¥4,782

[确认创建采购单]
[取消]
```

人工确认后才真正创建业务单据。

# 十四、为什么 Agent 不直接操作数据库

不采用：

```text
LLM
 ↓
生成 SQL
 ↓
MySQL
```

采用：

```text
Agent
 ↓
MCP Tool
 ↓
业务 API
 ↓
Service
 ↓
Repository
 ↓
MySQL
```

原则：

> LLM 决定“做什么”，传统程序决定“怎么做”。

这样能够减少：

- 数据错误
- SQL 注入风险
- 幻觉导致的错误写入
- 业务规则绕过
